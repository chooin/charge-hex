# 两个大型业务入口的完整 C 逻辑译文

`reconstructed/business_handlers.c` 整理了应用的两个入口：`0x0800B0DC` 整帧命令分发、`0x08009694` 固定 `55 AA` 帧的标识符/计数状态机。函数内部的入口、switch 分支、退出路径和关键内存写入均已翻译；外部依赖保留为 `bh_地址` 声明。本文件不是完整驱动工程，也没有声称找回原始名称。

依据包括 `firmware.bin`、GNU Thumb 汇编、REA/Ghidra 的全函数输出，并对 Ghidra 的寄存器返回值和调用参数按指令修正。特别是 `0x0800CA80` 有第五个栈参数、`0x0800B74C` 有四个输出指针和一个输入，而自动伪代码的函数原型并未完整恢复这些信息。

## `0x0800B0DC` 分发结构

每次进入都会写 `U32(0x200000C0)=750` 和 `U8(0x200000BC)=1`。命令来自 `frame[2]`，参数起点为 `frame[4]`。命令前的长度/XOR检查在调用者，不在本函数。

前缀 `frame[0]==0x55`：

| 命令 | 条件/行为 |
|---|---|
| `10` | 参数交给 `0800BE24` |
| `2C` | `U16(20000878)==3` 时交给 `0800C20C` |
| `2D` | 同上，交给 `0800C1C8` |
| `36` | 子选择1/2/3分别清 `20000ACC/ACE/AD0`；4/5按索引清 `AD2/AD4` 的一个位 |
| 其他 | 返回，不生成响应 |

**所有非55前缀**都走另一分支，原函数并没有限制必须是AA。响应经 `0800C7C4(command, n, 1, payload, 0x55)` 发送。

| 命令 | 参数/响应效果 |
|---|---|
| `01` | 返回 `0C 01` |
| `02` | 调 `BC38` 填充响应；长度为 `payload[0]+1` 的uint8截断值 |
| `04` | 通道字节 + 两个大端16位数，调用 `CA80`；返回通道/结果 |
| `05` | 调 `B74C`，返回通道及前两个16位值（5字节） |
| `07` | 返回全局两个数，第二个先除10，均按16位大端发送 |
| `09` | 两参数调 `BCAC`，返回00 |
| `0C` | 两参数调 `BC74`，返回请求通道 |
| `0D` | 调 `B6D4`；返回通道/16位结果，再调 `9E30(channel-1,4)` |
| `0F` | 调 `B708` 填25字节响应 |
| `14` | 模式0才调用 `CA80`，多一个大端16位参数，返回通道/结果 |
| `15` | 模式0才调 `B74C`；返回四个16位值，共9字节 |
| `18` | 参数交给 `BCD8(...,1)`，返回00 |
| `1E` | 调 `B7A8` 填23字节响应 |
| `23` | 返回17字节 `18 00 03 00 06` 后接12个00 |
| `27` | 模式3；按大端32位ID去重，调用 `CA80` 的第五参数来自frame[15]；返回6字节 |
| `2E` | 模式3；扩展通道查询，返回15字节，最后两个字节FF |
| `32` | 子选择1/2/3修改RAM字段并写FC58/FC5A/FC5C，返回00；子选择1保留有符号byte扩展 |
| `34/35` | 查询两个不同组的参数，6字节响应；无效子选择保留原栈字节行为 |
| `38` | 设置模式和参数，执行2500、14400、20、480等上限，逐项写Flash配置；返回00 |
| `39` | 查询对应模式和参数，10字节响应 |
| `3B` | 先返回00；参数0/1写F802=AAAA，参数0再调用复位入口63EC |
| 其他 | 不响应 |

两个 `__ARM_common_switch8` 表在 `B10E` 和 `B142`，已按helper的地址算法解码。表头为最大索引，超出范围使用默认表项；目标为表头地址加 `2*offset`，再按Thumb地址归一化。不能把表内字节解释为普通指令。

译文增加显式 `scratch[60]` 参数：原函数的局部响应缓冲并未统一初始化，`34/35` 的无效子选择会发送原栈上的六个字节。显式输入使这种行为可以有定义地重放；它是恢复接口设计，不是原函数的第二个参数。将scratch全清零属于另一个行为变更，未冒充原代码。

## `0x08009694` 标识符状态机

从 `20001024` 读取固定帧：`frame[2..5]` 是大端32位ID，`frame[6..7]` 是大端16位数。译文只使用identifier/amount/pending等分析名称，不把它们未经证据地断言为卡号/金额/时间。

译文完整保留这些内部阶段：

1. 功能开启、计时槽、数值范围门控。数值允许0..5000，另有特殊值AA33。
2. `20001018`记录匹配：55模式减向关系、66模式加向关系；或重新查12通道和历史ID数组。
3. 新请求组装：更新记录，生成5字节串口响应或AA33特殊上报；保留模式3的额外条件及计时槽写入。
4. 55模式确认：更新累计/计数、历史数组和模1000000的总量，写FC30、清记录，再生成数字token序列。
5. 66模式确认：按通道记录或历史记录两种路线清状态、饱和扣减、清记录、生成数字token并写FC30。
6. 两种数字token路径的差别：一条在非零数字后附加49，另一条不附加。源码保留了原始token字节，没有虚造其具体语音含义。

原代码中某些异常而重要的行为也被保留：历史索引在 `<12` 时自增，因此可能使用索引12；两条66模式路线中总量计算一处相加、一处相减；16位字段按原指令截断。`0x0800C6D8` 的清记录动作被内联，并核对其不修改R2/R3，消除了自动伪代码中无类型 `extraout_r3` 指针写入的歧义。

## 差分验证

运行 `python3 recovery/verification/check_business.py`。脚本用ARM GCC重新编译实际的 `business_handlers.c`，分别用Unicorn执行重编译C与原固件Thumb指令，比较低8KiB SRAM、外部调用次序、参数及发送载荷。

- 分发器10,752例：全部256种命令 × 3种前缀 × 2种模式 × 7种子选择器，加确定性随机参数与初始RAM。
- 标识符处理器采用随机状态及定向状态，覆盖确认、历史匹配、通道匹配、特殊AA33、饱和扣减、token输出等路线。
- 外部函数使用同一套确定性的模拟返回/输出，不执行Flash、UART、外设或完整子调用链。
- 指令覆盖参考 `full_assembly/instructions.json`，是有限测试访问过的指令数量，不是路径完备性或所有输入的数学证明。

最终数量、覆盖地址和源码SHA-256见 `verification/business_result.json`。任何新的C修改都应重跑该脚本。测试通过不代表真实板上时序、中断并发、外设错误处理或全固件行为已完成验证。
